# RCA — Deploy run 0c9c7574-9f0a-4053-9996-287c81861741 (scriptmate-8)

## Symptom
`build_image` failed in the **EAS OTA update** lane (Cloud Build step #7 `eas-update`). Metro export aborted:

```
iOS Bundling failed ... node_modules/expo-router/entry.js (1 module)
SyntaxError: node_modules/expo-router/entry.js: Cannot find module 'babel-preset-expo'
Require stack:
 - .../node_modules/@babel/core/lib/config/files/plugins.js
 ...
✖ Export failed
expo ... cli export ... --platform ios --platform android ... exited with non-zero code: 1
```

Same failure on two consecutive redeploys (0c9c7574 and 25ad3bfb). Last green run was 9b52d428.

## Root cause
`frontend/babel.config.js` uses the bare preset:
```js
presets: ['babel-preset-expo'],
```
which Babel resolves from the **project-root** `node_modules/babel-preset-expo`.

But `frontend/package.json` declares `babel-preset-expo` **only as a devDependency, pinned to `~54.0.10`**:
```
"devDependencies": { "babel-preset-expo": "~54.0.10", ... }
```
Meanwhile the production dependency `expo@~54.0.37` requires a **different** range, `babel-preset-expo@~54.0.12` (confirmed in `yarn.lock`: `expo@~54.0.37` block → `babel-preset-expo "~54.0.12"`). So the lockfile carries **two** resolved versions:
- `babel-preset-expo@54.0.10` (direct devDependency)
- `babel-preset-expo@54.0.12` (transitive, required by `expo`)

With two versions, yarn hoists only one copy to the top-level `node_modules/babel-preset-expo` and nests the other. In the EAS export install the top-level copy the bare specifier needs ends up absent (the dev-pinned 54.0.10 copy is not present at root / gets pruned, and the 54.0.12 copy required by `expo` is nested under `node_modules/expo/node_modules/...` rather than hoisted to root). Result: `@babel/core` cannot resolve `babel-preset-expo` from the project root → export fails.

## Verification status (honest)
- Confirmed from `yarn.lock` that `expo@~54.0.37` pulls `babel-preset-expo@~54.0.12` while the direct declaration is `~54.0.10` (two distinct resolved versions).
- Confirmed `babel-preset-expo@~54.0.10` installs cleanly on its own, even under `NODE_ENV=production`.
- **Could NOT reproduce the full frontend install/export in the eph sandbox** — `yarn install` of this Expo/RN dependency tree OOM-kills the sandbox (exit 137) on every attempt, even with `--ignore-scripts --network-concurrency 1` and a raised `--max-old-space-size`. So the hoist/prune mechanism is inferred from the lockfile + build log, not eph-verified end-to-end.

## Fix (apply in source, then re-trigger deploy)
Eliminate the version split so a single `babel-preset-expo` copy is deduped and hoisted to the project root.

In `frontend/package.json`:
1. Remove `babel-preset-expo` from `devDependencies`.
2. Add it to `dependencies`, aligned to the version `expo` requires:
   ```json
   "dependencies": {
     ...
     "babel-preset-expo": "~54.0.12",
     ...
   }
   ```
   (Moving it to `dependencies` also guarantees it survives any production-mode prune during the EAS install.)
3. Regenerate the lockfile so both references dedupe to one version: run `yarn install` in `frontend/` and commit the updated `yarn.lock`. After this there must be exactly **one** `babel-preset-expo@...` block in `yarn.lock`.

Optional belt-and-suspenders: add a yarn `resolutions` entry `"babel-preset-expo": "~54.0.12"` to force a single version tree-wide.

Do NOT change `babel.config.js` — the bare `presets: ['babel-preset-expo']` is correct and standard; the problem is purely dependency resolution.

## Why this is not a platform/manifest fix
The `eas-update` lane script lives in the deployer binary (not in the app image or a per-app manifest), so it cannot be changed per app. The defect is in the app's `frontend/package.json` / `yarn.lock`. Re-running the deploy on unchanged source will fail identically — the package.json fix must land first, then E1 re-triggers the deploy.
