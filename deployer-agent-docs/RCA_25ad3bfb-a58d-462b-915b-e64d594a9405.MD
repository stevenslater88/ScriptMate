# RCA — scriptmate-8 deploy run 25ad3bfb-a58d-462b-915b-e64d594a9405 (FAILED at build_image / eas-update lane)

## Verdict
The approved backend parser fix (`backend/server.py`, the two test files) is **not** the cause. The build failed in the **EAS OTA (`eas-update`) lane**, which on this template (`expo_mongo_base_image_eas`) runs **inside the same Cloud Build as the backend `docker-build` lane**. Because the single Cloud Build fails, the backend image is never promoted — so nothing shipped.

## Important platform reality (contradicts the "backend-only, lanes separated" assumption)
There is **no backend-only path** on `expo_mongo_base_image_eas`. The `eas-update` (Metro bundle + OTA publish) step is baked into the deployer's build stage and runs in parallel with the backend docker build in the *same* Cloud Build. It consumes the preview pod's `frontend/` working tree — **including the uncommitted `frontend/yarn.lock`**. So the uncommitted frontend lockfile change WAS pulled into this build and broke it. The deployer agent cannot skip or disable this lane (it lives in the deployer binary, not in editable manifests).

## Root cause
`babel-preset-expo` cannot be resolved from the frontend project root during Metro `expo export`. The uncommitted `frontend/yarn.lock` is in an **inconsistent, hand-edited state** that a clean `yarn install` would never produce:

- `frontend/package.json` → `devDependencies.babel-preset-expo: "~54.0.10"`
- `frontend/yarn.lock` contains **two separate** entries:
  - `babel-preset-expo@~54.0.10:` → version `54.0.10` (yarn.lock line 2779)
  - `babel-preset-expo@~54.0.12:` → version `54.0.12` (yarn.lock line 2807)
- `expo@54.0.37` requires `babel-preset-expo "~54.0.12"` (yarn.lock line 4039).

`~54.0.10` is satisfied by `54.0.12`, so a correctly generated lockfile would **dedupe both ranges to one** `54.0.12` install. The hand-edited lockfile instead keeps two split entries. During the lane's mid-build `npx expo install expo-updates` → `yarn add expo-updates@~29.0.20` (build log: "success Saved lockfile"), yarn re-hoists node_modules; with the split/duplicate entry + `babel-preset-expo` being a top-level **devDependency**, the top-level `node_modules/babel-preset-expo` is not left at a location resolvable from the project root, and Metro's babel lookup (from `expo-router/entry.js` via `@babel/core`) fails with "Cannot find module 'babel-preset-expo'".

## What was verified vs inferred
- VERIFIED (static, in eph pod on this run's pulled source): the duplicate/split `babel-preset-expo` entries in `frontend/yarn.lock`, the `~54.0.10` devDependency pin in `package.json`, and `expo@54.0.37`'s `~54.0.12` requirement. `babel.config.js` uses `presets: ['babel-preset-expo']`.
- VERIFIED (Cloud Build log): the exact Metro "Cannot find module 'babel-preset-expo'" export failure and the mid-build lockfile rewrite by `yarn add expo-updates`.
- NOT reproduced end-to-end in-pod: a full `yarn install` to reproduce the empty/mislocated node_modules was SIGKILL/OOM-killed in the sandbox (exit 137). The bundle failure itself is directly evidenced by the Cloud Build log, not re-run locally.

## Fix (frontend source — owner: E1 / main agent, in the preview pod `save-script-verify`)
Pick ONE; option A is simplest and matches the user's intent that this lockfile change is unrelated to the backend deploy:

**A. Discard the uncommitted `frontend/yarn.lock` change** (revert to the committed lockfile that last deployed successfully, run 9b52d428). That lockfile is known-good for the EAS lane.

**B. Regenerate a clean, consistent lockfile:**
```
cd frontend
rm -f yarn.lock && rm -rf node_modules
yarn install
```
Confirm the result dedupes `babel-preset-expo` to a single `54.0.12` entry (`grep -c 'babel-preset-expo@' yarn.lock` should reflect a single merged range, not two split `~54.0.10` / `~54.0.12` blocks), and that `node_modules/babel-preset-expo` exists at the project root.

Optionally also align `package.json` `devDependencies.babel-preset-expo` to `~54.0.12` to match `expo@54.0.37` and avoid future split resolutions.

**Do NOT** change Expo/RN/Gradle/SDK versions, package/applicationId, signing, or any backend file — the backend parser fix is correct and untouched by this issue.

Re-trigger the deploy. The backend parser fix will ship together with a clean frontend bundle. (No manifest change is applicable; this is purely a frontend lockfile source fix.)
